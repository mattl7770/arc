# ARC — Exhaustive Code Review

**Date:** 2026-08-23  ·  **Branch:** `claude/arc-comprehensive-review-eca7e6`  ·  **Scope:** every file in the app

## Method

A multi-agent static review. The codebase (287 TS/TSX files, 33 SQL migrations, the headless test suite, and build config) was partitioned into **73 review units**. Each unit was:

1. **Reviewed** by a dedicated agent doing a deep, invariant-driven bug hunt (ARC’s load-bearing rules — FK pragma, forward-only migrations, exact biomarker matching, renderers-compute-nothing, HealthKit `Quantity` traps, local-first privacy, etc. — were given to every agent).
2. **Adversarially verified** by a second, independent agent that re-derived every claimed defect against the source, **refuted false positives**, and hunted for anything the first agent missed.

Only findings that survived verification are listed. Each is tagged `CONFIRMED` (reproduced against the source) or `PLAUSIBLE` (very likely, not fully provable by static analysis alone). Nothing here was run on a device — `node_modules` is absent — so this is static analysis; a few items are latent until the pending EAS build.

> Note: the tools/tests themselves were reviewed too. Several dozen candidate findings were **refuted** during verification and are deliberately not listed.

### H1. expo-status-bar listed in app.json plugins array (has no config plugin) breaks EAS builds

- **Where:** `app.json:25`  ·  _xcut-config_
- **Verdict:** CONFIRMED (confidence: medium)
- **What:** app.json's expo.plugins array lists "expo-status-bar". expo-status-bar is a JS-only component library (it is imported and rendered as <StatusBar style="dark" /> in app/_layout.tsx lines 5/125/235) and ships no config plugin (no app.plugin.js / no plugin export). Expo's config-plugin resolver requires every entry in the plugins array to resolve to a valid config plugin function; an entry that resolves to a module without one throws rather than being ignored.
- **Trigger:** Running `expo prebuild` or triggering an EAS build (the project has a 'pending EAS build' per the memory notes, so this is latent, not yet exercised): during the 'Resolving plugins' phase Expo throws `PluginError: Failed to resolve plugin for module "expo-status-bar"` and the prebuild/build aborts before compiling. Every native build fails until the entry is removed.
- **Fix:** Remove the "expo-status-bar" string from the app.json plugins array (line 25). The component continues to work via the import in app/_layout.tsx; it never needed a plugin entry.

### H3. A model item with grams:0 blocks saving the entire estimated meal

- **Where:** `app/meal-estimate.tsx:362`  ·  _screen-meal-estimate_
- **Verdict:** CONFIRMED (confidence: high)
- **What:** meal_items enforces CHECK (grams IS NULL OR grams > 0) (db/migrations/0014_food_catalog.sql). But a review row can carry grams:0 unchanged into the insert. parseMealEstimate keeps a JSON grams:0 as 0 (num() accepts >= 0, estimate.ts:167-169,210), groundMealEstimate leaves a grams<=0 item ungrounded (estimate.ts:427), and toReview sets base.grams = item.grams = 0 (line 225) with gramsText='0' (line 233, because item.grams is not null). parseGrams('0') returns null (rejects g>0, line 153), so currentPortion falls back to base and returns p.grams=0 (lines 158-174). save then builds NewMealItem with grams:0 (line 362), logMealWithItems inserts it, the CHECK fails, the whole transaction rolls back, and the catch shows the generic 'Couldn't save the meal. Try again.' There is no per-row validation, so the user cannot tell which row is at fault and 'Try again' never succeeds until they happen to edit the '0' to a positive number or remove that row.
- **Trigger:** User photographs / describes a meal; the model returns an item with grams:0 (e.g. black coffee, water, salt, a negligible item — plausible given the prompt asks for a grams number). The review shows that row with '0' in the grams field and a normal kcal. User taps Save meal. The CHECK(grams > 0) violation rolls back logMealWithItems and the screen shows 'Couldn't save the meal. Try again.' The whole meal (all items) cannot be logged, with no indication that the 0 g row is the cause; repeated taps keep failing.
- **Fix:** Normalize non-positive grams to null before it can reach the insert. Simplest: in toReview set base.grams to (item.grams != null && item.grams > 0 ? item.grams : null) and gramsText to '' when grams<=0; or in save/currentPortion coerce a grams value of 0 (or <=0) to null so it stores as 'not recorded' rather than violating the CHECK. Keep parseGrams and the base normalization consistent (both should treat 0 as 'no grams').

### H5. Editing a past workout silently drops then permanently deletes free-text sets

- **Where:** `app/workout-live.tsx:231`  ·  _screen-workout_
- **Verdict:** CONFIRMED (confidence: high)
- **What:** blocksFromWorkout() rebuilds the editor's blocks from a stored session, but any set whose exerciseId is null is discarded: line 231 sets built = s.exerciseId == null ? null : buildBlock(...) and line 232 does if (!built) continue;, so the set is never pushed into any block. Free-text (null exerciseId) sets are a normal, documented case - workout-log.tsx logs every set with no exerciseId and relies on resolveExerciseByName, which is confidence-gated and returns null for genuinely custom movements (insertSet docblock in exercise.ts; StoredSet.exerciseId is string|null). LiveBlock.exerciseId is typed non-null (line 126), so the editor cannot represent such a set. Dropped sets are merely hidden on open, but the editor's save (replaceWorkout) does DELETE-all-then-reinsert from the visible blocks only, so the omitted sets are erased on the next save. It also corrupts ordering: bench(matched)->custom(free-text)->bench(matched) collapses to one merged bench block, destroying the interleave.
- **Trigger:** User logs a session in workout-log.tsx with a custom movement (e.g. Sled push) whose name does not confidently resolve to a catalog id, so its sets store exercise_id = NULL. Later they open that session from Recent sessions (exercise.tsx -> /workout-live?workoutId=), which shows it missing the sled-push sets. They tweak a rep and tap Save changes; replaceWorkout deletes all workout_sets and reinserts only the visible blocks - the sled-push sets are gone permanently, no undo, no server copy.

On finish/replaceWorkout pass exerciseId: b.exerciseId (null) so insertSet keeps the free text. Same treatment also fixes the catalog-deleted case (getExercise null).

### H6. saveMealAsRecipe writes resolved lines with NULL resolved_by, causing silent re-pricing and provenance corruption

- **Where:** `src/lib/db/repositories/recipes.ts:79`  ·  _found independently by: repo-recipes, xcut-schema-contract_
- **Verdict:** CONFIRMED (confidence: high)
- **What:** insertIngredient's INSERT (lines 79-100) never writes the resolved_by column, so every row it creates gets resolved_by = NULL (the schema has no default). This is fine for the unresolved paths (createRecipe, addIngredient, applyRecipeRevision all pass grams=NULL), but saveMealAsRecipe (lines 715-731) deliberately builds RESOLVED lines: when a meal item has usable grams+kcal it sets grams/kcal/macros/micros non-null while resolved_by stays NULL. This violates the load-bearing 0034 invariant 'resolved_by IS NULL <=> grams IS NULL' that the repository is solely responsible for maintaining (the schema cannot enforce it as a CHECK; see the 0034 header and unresolveIngredient's comment at lines 443-445). Because catalogResolveRecipe (src/lib/recipes/estimate.ts:131) and unpricedLines (estimate.ts:151) define 'unresolved' as resolved_by === null — NOT as isResolved(grams/kcal) — these copied-from-meal lines are treated as unpriced and re-processed. recipe-detail.tsx runs catalogResolveRecipe on every open (recipe-detail.tsx:169), and its own doc (lines 935-937) states the skip depends on 'a provenance at all'.
- **Trigger:** User logs a meal whose items were priced by the model or by a food that was later edited/deleted in the catalog (or whose stored name matches a different catalog food than the original). User taps 'Save as recipe' (app/meal-detail.tsx:441 -> saveMealAsRecipe): each item lands as a resolved line (grams+kcal+macros copied) but resolved_by = NULL. User opens the new recipe -> recipe-detail.tsx:169 calls catalogResolveRecipe. For each such line, line 131 does NOT skip it (resolved_by is NULL), lineGrams parses the mass from raw_text, searchFoods finds a confident name match, and resolveIngredient OVERWRITES the copied snapshot with a fresh catalog computation and stamps resolved_by='catalog'. Result: the nutrition the meal actually recorded is silently replaced with re-derived numbers from a possibly-different food (an AI-estimated item is relabeled as a measured 'catalog' number; a since-edited food yields different macros; a name-ambiguous item points at the wrong food). This is exactly the snapshot-survives-catalog-churn and provenance-honesty guarantee the 0034 design exists to protect.
- **Fix:** Have insertIngredient write resolved_by. Add resolved_by to the FullIngredient type (line 56-66) and to the INSERT column list/values (lines 79-100). In saveMealAsRecipe (lines 715-731), pass resolved_by for resolved lines so the coupling holds and catalogResolveRecipe skips them — e.g. resolved_by: resolved ? (item.food_id ? 'user' : 'ai') : null (or propagate the meal item's own provenance if tracked). Minimum correct fix: any line inserted with non-null grams must carry a non-null resolved_by so 'resolved_by IS NULL <=> grams IS NULL' is never violated.

### H7. No re-entrancy guard lets concurrent sync passes double-publish body samples to Apple Health

- **Where:** `src/lib/health/publish.ts:174`  ·  _lib-health_
- **Verdict:** CONFIRMED (confidence: medium)
- **What:** Neither syncHealthData nor publishBodyMetrics has any in-flight/mutex guard. Two passes can run concurrently: the boot auto-sync (sync.ts:96 void syncHealthIfEnabled) or the AppState 'active' listener (sync.ts:97) overlapping with a manual Settings sync (settings-health.tsx:172/196/218, which bypass the shouldAutoSync throttle entirely). Both passes call getHealthPublishState, read the SAME cursor, walk publishableBodyAfter over the SAME body_metrics rows, and call deps.save for each sample twice.
- **Trigger:** User taps 'Sync now' in Settings during a slow first-enable 90-day sync (or backgrounds/foregrounds during a long MAX_SYNC_DAYS catch-up while the boot sync is still awaiting XPC). Both publishBodyMetrics invocations see the same un-advanced cursor and publish every pending weight/body_fat/waist row twice. saveQuantitySample returns a new UUID with nowhere to store it, so ARC can never delete the duplicates — permanent duplicate rows land in the user's Apple Health medical record, the exact harm publish.ts is architected to prevent.
- **Fix:** Guard the whole pass with a single shared in-flight Promise (module-level `let inFlight: Promise<...> | null`) so overlapping calls await the same pass instead of starting a second; at minimum serialize the publish walk. The inbound upsert is idempotent and safe, but the outbound publish must never run twice concurrently.

### H8. storeProgressPhoto drops date_origin, corrupting EXIF-date provenance

- **Where:** `src/lib/media/progress-photo-store.ts:142`  ·  _found independently by: lib-media, screen-photos_
- **Verdict:** CONFIRMED (confidence: high)
- **What:** storeProgressPhoto builds the insertProgressPhoto payload by hand and forwards taken_on, taken_at, pose, source, asset_id, working_file_name, original_file_name, is_important and notes — but NOT date_origin, even though CapturedProgressPhoto carries it (it is `& Omit<NewProgressPhoto, 'working_file_name'|'original_file_name'>`, and NewProgressPhoto includes date_origin). Because the field is omitted, insertProgressPhoto (src/lib/db/repositories/progress-photos.ts:65) applies its `photo.date_origin ?? 'manual'` default, so EVERY imported photo is stored with date_origin='manual' regardless of where its date actually came from. This is the one field the whole EXIF-date-honesty flow exists to record: app/progress-photo-add.tsx:192 carefully computes 'exif' | 'asset' | 'manual', but that computed value is thrown away one layer down. taken_at IS forwarded, so a photo also ends up in the self-contradictory state of holding a real EXIF instant (taken_at set) while claiming date_origin='manual'.
- **Trigger:** User imports a photo taken last year whose EXIF DateTimeOriginal + OffsetTimeOriginal parse cleanly. assetPhotoDate returns origin:'exif' with a real takenAt; the add screen sets date_origin:'exif' (unedited). importProgressPhotos -> storeProgressPhoto inserts the row WITHOUT date_origin, so it is stored as 'manual'. The detail screen (app/progress-photo-detail.tsx:235) then renders DATE_ORIGIN_LABEL['manual'] — telling the user they typed the date in themselves when it was in fact read from the photo. The stored row also contradicts itself (taken_at present, date_origin='manual'). The honesty invariant the feature is built on is violated silently for every EXIF- and asset-dated import.
- **Fix:** Forward the field in the insert payload: add `date_origin: photo.date_origin ?? 'manual',` to the object passed to insertProgressPhoto in storeProgressPhoto (progress-photo-store.ts ~line 143). No other NewProgressPhoto field is missing, so this single addition restores the provenance flow.

### M1. Per-serving 100%-macro food is un-saveable (float overshoot of the 0–100 CHECK)

- **Where:** `app/food-new.tsx:157`  ·  _screen-food_
- **Verdict:** CONFIRMED (confidence: high)
- **What:** When the entry basis is 'serving', per100(text) converts a per-serving macro to per-100 g via n * (100 / servingGramsNum) with no rounding (lines 156-162). For the common case where a macro equals the serving grams (a ~100%-macro food), IEEE-754 yields 100.00000000000001 instead of 100. per100Problem (line 119) then evaluates macros.some((m) => m > 100) as true and returns 'A macro can't exceed 100 g per 100 g of food.', so canSave is false and Save is disabled with a misleading message. Independently, if the value reached the DB it would violate the schema CHECK protein_g_100g/carbs_g_100g/fat_g_100g <= 100 (db/migrations/0014_food_catalog.sql) and be silently swallowed by the save() try/catch (lines 192-196). Per-serving is the documented 'label way' of entering foods, and 100%-macro foods (olive oil, pure sugar, protein isolate) are exactly the staples a user would add as customs.
- **Trigger:** Tap 'Per serving'; enter Serving grams = 14, Fat g = 14 (olive oil, 1 tbsp label). factor = 100/14 = 7.142857142857143; per100('14') = 7.142857142857143 * 14 = 100.00000000000001. macros100[2] = 100.00000000000001 > 100, so per100Problem returns the macro-cap error, canSave is false, and the legitimate food cannot be saved. Same for carbs (7 g in a 7 g sugar serving) and any isolate.
- **Fix:** Round each converted per-100 g value before the bounds check and before createFood, e.g. const round2 = (v: number | null) => v === null ? null : Math.round(v * 100) / 100; apply to kcal100 and every entry of macros100. 100.00000000000001 then becomes exactly 100, clearing both per100Problem and the DB CHECK.

### M2. GroceryEntryRow keeps stale local qty state, silently overwriting a line-level quantity edit

- **Where:** `app/grocery.tsx:975`  ·  _screen-grocery_
- **Verdict:** CONFIRMED (confidence: high)
- **What:** GroceryEntryRow seeds its editable quantity from `useState(item.qty_text ?? '')` and NEVER re-seeds it when the underlying item's qty_text changes. Because each GroceryEntryRow is keyed by item.id (line 952), a reload after an edit does NOT remount it — the local `qty` state persists while the `item` prop refreshes. This is exactly the stale-controlled-input hazard the authors explicitly fixed in GroceryLineEditor (lines 819-841 add a render-phase seed-resync for that reason), but GroceryEntryRow was left without the equivalent guard. saveQty (line 977-983) then compares the stale local `qty` against the FRESH `item.qty_text` prop and writes the stale value back when they differ.
- **Trigger:** Multi-entry line 'milk' with entries x(qty='1 cup') and y(qty='2 cup') -> qtyDisplay='3 cup'. Open the line editor. (1) Edit the LINE-level qty field (GroceryLineEditor) to '1 gallon' and blur: updateGroceryLine writes x.qty_text='1 gallon', y.qty_text=null (grocery.ts:315-330), reload fires. (2) GroceryLineEditor re-seeds correctly, but the two GroceryEntryRow instances are not remounted, so their fields still show the stale '1 cup' and '2 cup' — already visibly contradicting the DB. (3) User focuses entry x (showing stale '1 cup') and blurs. saveQty computes trimmed='1 cup', reads item.qty_text (fresh)='1 gallon', they differ, so it calls updateGroceryItem(x,{qty_text:'1 cup'}) — silently reverting the '1 gallon' the user just set on the line. The just-entered quantity is lost with no indication.
- **Fix:** Mirror GroceryLineEditor's seed-tracking pattern in GroceryEntryRow: track a `seed` of item.qty_text and, during render, if `seed !== (item.qty_text ?? '')`, re-seed both `seed` and the `qty` field so external DB changes to this entry refresh the input while in-flight typing is preserved. Alternatively remount entry rows on data change by keying on `item.id + (item.qty_text ?? '')`, though the seed pattern is safer for in-progress edits.

### M3. Seed rounding to 2 decimals is stored verbatim, silently corrupting small/high-precision biomarker values

- **Where:** `app/lab-import.tsx:161`  ·  _screen-labs_
- **Verdict:** CONFIRMED (confidence: medium)
- **What:** Every review row's editable value is seeded with String(round(m.value)) where round() = Math.round(n*100)/100 (line 105-107), and Save stores exactly that seeded text via parseValue(r) (lines 207, 224-231) unless the user hand-edits it. The rounding is applied uniformly to ALL rows, including 'matched' rows that underwent no unit conversion, so a value the model transcribed verbatim from the PDF is truncated to 2 decimal places before it is ever persisted. For values below ~0.005 the stored number becomes 0. The rounded value is also what the review field displays, so the user cannot easily notice the loss during review (0.014 looks like a plausible reading as 0.01).
- **Trigger:** A Function panel prints an ultrasensitive PSA of 0.014 ng/mL (a real, clinically meaningful 3-decimal reading). The model extracts value=0.014; the row is 'matched' or 'new'. valueText is seeded as String(round(0.014)) = '0.01'. The user glances at the review row (which shows 0.01) and taps Save. lab_results stores 0.01 — a ~30% error on the trend point. A converted value that resolves to 0.003 is stored as 0, planting a literal zero on the series. The doc rationale ('conversions produce more decimals') only justifies rounding converted rows, not matched ones, and does not anticipate zeroing sub-0.005 values.
- **Fix:** Do not round the seed for 'matched'/'new' rows (their value is already the printed number) — seed valueText with String(m.value). If trimming conversion noise is desired, round only when m.status === 'converted', and use a precision that scales with magnitude (e.g. keep at least 3 significant figures) rather than a fixed 2 decimal places, so small values are not zeroed.

### M4. Pricing spinner stuck true and model pass never retries after mid-stream blur

- **Where:** `app/recipe-detail.tsx:270`  ·  _found independently by: screen-recipe-detail, xcut-rn-lifecycle_
- **Verdict:** CONFIRMED (confidence: high)
- **What:** priceRemaining() starts the model pricing stream, sets pricing=true (line 254), records askedRef.current=key BEFORE the await (line 251), and returns a cleanup () => controller.abort() (line 274) that useFocusEffect runs on BLUR. When the screen blurs mid-stream (e.g. tapping Edit / Edit in words / Manage folders / a food search, all router.push that keep this screen mounted underneath), the controller is aborted. Every promise handler is guarded by `if (controller.signal.aborted) return`, INCLUDING the finally at line 270 `if (!controller.signal.aborted) setPricing(false)`. Because the component is only blurred (not unmounted), state persists: pricing stays true forever. On re-focus, priceRemaining runs again but askedRef.current still equals key (it was set before the abort and is never reset), so it early-returns at line 249 without starting a new pass or touching pricing. Net result: the 'Working out the lines that aren't in your food catalog…' spinner (line 508) and the 'Working the numbers out now.' gate copy (line 579) show permanently, and the automatic model pricing never completes for the remaining unpriced lines during that mounted visit.
- **Trigger:** Open a recipe with volumetric/countable lines the catalog can't price (e.g. '2 tbsp butter') with a model key set. The model pass starts (spinner shows). Before it finishes, tap 'Edit' (or 'Edit in words'/'Manage folders'). Blur aborts the stream. Return to the recipe: the spinner is still spinning, the Per-serving block reads 'Working the numbers out now.', and the lines are never priced no matter how long you wait — only fully popping and re-pushing the screen recovers it.
- **Fix:** Clear the stuck state on abort. In the returned cleanup reset both flags so a re-focus retries: `return () => { controller.abort(); setPricing(false); askedRef.current = ''; };`. (Setting pricing false on a truly-unmounted component is a harmless no-op in React 18.) Alternatively make finally unconditional — `.finally(() => setPricing(false))` — and reset askedRef in the abort cleanup so the once-per-set guard doesn't permanently suppress the retry the abort comment says it expects.

### M6. FK-pragma invariant is supplied by the harness, so a device-only regression stays green

- **Where:** `src/components/exercise/freshness-display.ts:98`  ·  _screen-train-tab_
- **Verdict:** CONFIRMED (confidence: high)
