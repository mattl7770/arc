## 2. How detectable, plainly

**Garmin can see everything it chooses to log.** Every request to its servers carries your account token, so nothing here is anonymous — if Garmin ever looks at your account, it lands on you. The question is never "can they see it" but "do they look, and do they act."

**What every request unavoidably reveals (route H specifically):**
- **Garmin's own app client ID, inside the token.** The token ARC holds is minted for one of Garmin's app IDs; that ID rides in the token and is read on every call. There is no version of route H that presents ARC's identity in the token. This single fact makes "ARC is not the Garmin app" trivially knowable to Garmin. (checked 2026-09-26: the first three sentences hold, the last does not. python-garminconnect's `client.py` (master, read today) exchanges the ticket with Basic auth `client_id:` and **no secret**, and the token is a JWT whose `client_id` claim is Garmin's (for example `GARMIN_CONNECT_MOBILE_IOS_DI`). So the token makes ARC look *like* the Garmin app. ARC becomes knowable through the next three bullets and through its headers: an honest `User-Agent` names it outright; copied Garmin headers do not, but copied **Android** headers sent from an iOS network stack would be a mismatch, so a build that copies headers should copy the iOS app's.)
- **The endpoint mix.** ARC reads a small fixed set (HRV, sleep, SpO2, respiration, stress, Body Battery, Training Readiness, VO2 max) and never uploads or makes the many feed/sync/social calls Garmin's app makes. The *absence* of app traffic is itself distinctive.
- **Volume and shape.** ~6–10 reads a day, a few app-opens. Distinctive by being low and regular — the opposite of what rate limits hunt.
- **IP / network origin.** A home or cellular IP, same as the Garmin app — this is the biggest thing in your favour.

**What Garmin has actually deployed (checked live 2026-09-26):**
- Sign-in (`sso.garmin.com`) sits behind Cloudflare bot management and an armed-but-off reCAPTCHA. A **real browser engine passes it**; that is exactly what a WKWebView sign-in is. (checked 2026-09-26: confirmed. The mobile sign-in page (`clientId=GCM_IOS_DARK`) returned today with `Server: cloudflare`, a `__cf_bm` bot-management cookie, Cloudflare's `challenge-platform/…/jsd/main.js` detection script, a reCAPTCHA Enterprise site key, and `CaptchaEnabled: false`. Garmin's own iOS app signs in on this same page in a web view, which is why the library copies a WKWebView user agent for it.)
- Scripted logins to the mobile login endpoint have returned a blanket 429 since 2026-03-17, worldwide — but Garmin's app and browser logins kept working throughout. This targets *scripts*, not people signing in by hand. (checked 2026-09-26: "since" overstates it. The blanket 429 began 2026-03-17 ([garth #217](https://github.com/matin/garth/issues/217): "Browser login and the Garmin Connect mobile app both work fine"). The libraries then worked around it, and by 2026-05-22 python-garminconnect's maintainer wrote that it "is just working for all my users". What remains is the defence behind it (next bullet), not a blanket block.)
- (checked 2026-09-26, missing from this list: **TLS fingerprinting.** A Garmin forum thread opened 2026-03-30 ([433892](https://forums.garmin.com/apps-software/mobile-apps-web/f/garmin-connect-web/433892/tls-fingerprinting-blocks-third-party-clients)) reports Cloudflare fingerprinting the TLS handshake on the Connect APIs, breaking non-browser clients. python-garminconnect now impersonates Safari-iOS and Chrome handshakes through `curl_cffi` and notes that "different TLS fingerprints land in different Cloudflare rate-limit buckets". This is the discriminator that matters most today. It is H's biggest technical advantage: ARC's `fetch` on iOS uses Apple's own networking stack, so its handshake is an ordinary iOS app's. It is also why RunGap, a native iOS app, did not break on 2026-03-17 when the Python clients did (its break came on 03-27 and was fixed the same day). The computer job (I) has to impersonate a handshake instead.)
- The data API adds extra 401s specifically for **datacenter/cloud IPs**; home networks were unaffected. (checked 2026-09-26: a community observation, not a Garmin statement, from one garth #217 comment (2026-03-21), plus one user whose tokens moved to a server were "invalidated" within days. go-garmin's docs (2026-09-15) add that Garmin "aggressively rate-limits datacenter IPs", so 429s as well as 401s.)
- Garmin's official developer program is **frozen to new applicants** since spring 2026, so there is no official on-ramp to wait for. (checked 2026-09-26: the overview page still reads "Stay tuned for more updates on the program", with no form. The "spring 2026" date comes from the5krunner alone.)
- Device attestation (Apple App Attest / Play Integrity): the Android app calls Play Integrity, but the evidence points to it gating device-bound features, not the web sign-in or the data reads route H uses. Treat as "not blocking today, unverified for the future." (checked 2026-09-26: no evidence was found for what it gates. The only source found, a GrapheneOS forum thread of 2025-08-14, shows Connect for Android 5.16 *calling* Play Integrity on a phone that fails device integrity, with the app still working. The stronger evidence that attestation is not enforced on H's path today is that python-garminconnect gets tokens and data from a plain Python process, with no device at all. Nothing was found either way about App Attest on iOS. The conclusion stands; the "device-bound features" part is a guess.)

**Detectable vs acted-on — the distinction that matters:**
- **Detectable:** ~100% if Garmin deliberately audits. The tells above are unavoidable.
- **Acted on, at your volume:** low. Every enforcement Garmin has used targets a signature *shared by thousands* (a library's fingerprint, datacenter IP ranges, bursts of logins). ARC is a population of one; no one writes a rule for a single quiet user. The realistic path to harm is being caught as collateral by a broad rule, and the ~26,500+ far-louder Home Assistant installs would trip that rule and report it first. (checked 2026-09-26: Home Assistant's analytics (`custom_integrations.json`, fetched today) count **5,261** installs of `garmin_connect`, and only installs that opted in to analytics are counted. ~26,500 is not a published figure; it matches a ×5 guess at the opt-in rate. "Far louder" holds: the integration polls every 5 minutes by default. Two exceptions to "shared by thousands": the per-account 48–72 h login block and the forced password resets of 2022–23 both hit single accounts, and both followed repeated scripted or failed logins.)

**Separate the two moments of route H:**
- **The one-time sign-in** happens by hand on Garmin's real page in a real browser engine. Rare event, low risk — this is exactly how RunGap (an iOS app signing in unofficially since 2014) has survived 12 years. (checked 2026-09-26: not "exactly". RunGap's help article (created 2014-04-07, edited 2024-08-23) has you type your Garmin username and password into **RunGap's own form**, so RunGap signs in programmatically. That is a heavier pattern than H's hand sign-in on Garmin's page. Its 12 years as a paid App Store app with no reported account action is still good evidence, and if anything it is stronger evidence for H.)
- **The daily reads** are the ongoing exposure, and they are the low, residential GETs above. This is where "1–3 breaks a year" lives, never "suspension."

**The terms angle, stated factually.** Garmin's Terms of Use (effective 2026-04-01) forbid scraping by means Garmin didn't provide, and forbid "forging headers or otherwise manipulating identifiers to disguise the origin of any message." Route H breaks the scraping clause outright. Whether it also breaks the header clause depends on a build choice (§6). (checked 2026-09-26, clauses re-read verbatim today: the scraping example reads "Using any process, **whether automated or manual**, that accesses, copies, or scrapes content from the Site through any means not purposely made available through the Site". On the header clause, copying Garmin's app headers breaks it on plain wording. But even an "honest" build presents Garmin's client ID at the token exchange, which is what the 2026-09-25 spike called "arguably" manipulating identifiers. So the build choice decides between a plain breach and an arguable one, not between a breach and none.) This is a rule you can read in plain English; no amount of low practical risk removes it. That is a values call, and it is yours — my job is to make it visible.

**The numbers do not change the earlier recommendation (in-app link).** They confirm H's *account* risk is low and relocate the real risk to breakage (65–95%/yr, recoverable) and one honesty question. So: (checked 2026-09-26: the ranking survives the corrections. The ban figure is now a stated judgment, not a derivation. Breakage is ~40–98%/yr depending on how many of the observed breaks carry over, with ~4–60 days lost in a typical year. The TLS finding makes H *stronger* against I, while the client-ID point makes H's terms position slightly *worse* than stated. None of this reorders the three options for "simplicity and maximum data".)

**1st — H, with Health Sync as backup + one full export.** ~94–100% coverage, ~15 min setup then ~0.5–1 h/yr, $3.99. (checked 2026-09-26: only **if** the Stage-0 test shows Health Sync delivering the CIRQA's HRV. Its store page still names no Garmin HRV. If the test fails, H's outages stale HRV too, and the backup is typing `hrv`.) **The trade:** the scraping clause, 1–4 rebuild cycles/yr, a token on the phone, and — depending on the build choice — the header clause.

> **The gate that actually decides it (§2's honesty fork):** route H works today for the community only because their clients send Garmin's *own app* identity on API calls. An **honest** ARC — sending its own identity — is untested and, on the balance of evidence, may simply be refused data (30–70% chance). So the on-device spike must **test the honest request first.** If honest works, you get maximum data with a clean conscience on the header clause. (checked 2026-09-26: a *cleaner* conscience, not a clean one. If it doesn't, you face a genuine choice: copy Garmin's app headers (works, but that is the clause named in plain English) or fall back to route F. Do not bury this inside "it works."

**2nd — if you want zero terms risk: intervals.icu (F) + Health Sync.** ~50% coverage, HRV automatic, ~20 min setup then nothing, no fix builds. You give up SpO2, respiration, stress, Training Readiness, HRV status, Training Status. Clean under Garmin's terms; your data on their servers.

**3rd — if H's spike fails but you accept the terms: the computer job (I).** Same maximum data, cheaper fixes, but a computer must be on each morning and Python is what Garmin targets.

**Always, regardless: Stage 0 today** — turn Pulse Ox to "During Sleep," request the full export, test Health Sync's HRV. None of it bends a rule, and the export is your insurance for the ~0.1% case.

Recommended: **decide this consciously, don't default into it.** My lean: if honest fails, prefer route **F** (clean terms, fewer metrics) over copying app headers — unless the missing metrics (SpO2, respiration, Training Readiness) genuinely change how you'd act, in which case accept the trade with eyes open and record it in the ADR.

**Q3. Run the dev spike on a throwaway Garmin account?**
Recommended: **yes.** It drops the temporary-block risk from 10–25% to 1–3%. Touch your real account only once the flow is proven. (checked 2026-09-26: the 10–25% and 1–3% are judgments. The recorded blocks all followed scripted or failed logins, and none came from hand sign-ins in a browser engine. One limit: a throwaway account has no band, so it can prove the sign-in, the ticket capture, the exchange and whether the honest identity is served, but not which CIRQA figures actually arrive. That needs one pass on the real account.)

**Q4. Health Sync as the automatic HRV backup?**
Recommended: **yes, if the Stage-0 test shows HRV arriving.** It uses Garmin's official link, so it survives the same Garmin change that breaks H. Do not use Vitals Sync or HRV Sync as the backup — same unofficial method, breaks the same day.
