  - **What is deleted:** rows in `log_entries` carrying `seed: true` in their presentation-extras JSON — the eleven-item mock day Home planted on any date that produced no protocol entries, until the fabrication was stopped on 2026-08-07 (entry under *Home screen* above). It replanted on every new day for a user with no protocols, so the device holds **many days** of it. Nothing else is touched: `log_entries` is the only table named.
  - **The exact predicate**, and why each term is there: `json_type(value,'$.seed') = 'true'` is the marker — `insertMissionItem` (`repositories/mission.ts`) is the **only writer** of that key anywhere in the repo, and every version of that line in git history emits the JSON literal `true`. It is deliberately **`json_type`, not `json_extract(...) = 1`**: json_extract coerces, so the looser form would also delete a hypothetical `{"seed":1}`. Three further terms can only ever *shrink* the delete set — `json_extract(value,'$.adhoc') IS NULL` (this is `PLANNED_ROW_SQL` reproduced exactly, so the DELETE reasons about "is this a mission row" identically to `listMission` / `countMissionEntries` / the mode re-derive, and the owner's Log-tab notes and metrics are protected), plus `json_extract(value,'$.generated') IS NULL` and `protocol_id IS NULL`, which fence off real protocol-generated plan rows on two independent columns. **Ambiguity therefore resolves toward keeping a row** — leaving one fake row is a nuisance, deleting one real row is unrecoverable.
  - **Status is deliberately NOT filtered.** Seeded rows die in `pending`, `completed`, `partial` and `skipped` alike. A completed fake supplement stack is still fabricated, and the completed ones are exactly what corrupts adherence history and what `get_today_snapshot` was reporting to the Coach as genuinely-done work. Adding `AND status = 'pending'` would keep the most damaging rows — the migration header says so in as many words.
  - **`daily_logs` are never deleted**, including days the purge empties completely: a `daily_log` carries the owner's own `summary`, `notes` and `overall_adherence_score`. An empty day is the honest post-purge state and Home renders its empty state over it. No cascade exists out of `log_entries` (nothing anywhere declares `REFERENCES log_entries`), and its only trigger is `AFTER UPDATE`, which a DELETE does not fire.
  - **Recovery, stated honestly — do NOT treat this as a rollback you can rely on.** `backupBeforeMigrate` (entry above) snapshots via `VACUUM INTO` before `migrate()` runs, and both of its guard conditions hold for this migration (device at `user_version` 28, 0029 pending), so 0029 *is* covered by it. **But that call is wrapped in try/catch and on failure merely `console.warn`s and proceeds** — a pre-release app must not brick on a backup hiccup. The snapshot is **best-effort, not guaranteed**, it is written next to the DB under `Library/` (`arc.db.pre-migrate-<ts>.bak`, see the Documents-privacy caveat), and nothing prunes or verifies it. If the purge is ever regretted, that file is the only route back and it may not exist. There is no server backup — this database is the owner's only copy.
  - **Proof:** `db/migrate.test.mjs` §§5–7 (33 assertions total in the suite). §5 stages a database at `user_version` 28, inserts a **hostile 30-row mixture via raw SQL** — seeded rows in all four statuses across several days; ad-hoc captures; protocol-generated and mode-injected rows; hand-added rows; a user note whose *text* contains "seed"; `seed` nested at `$.meta.seed`; `value` NULL, `{}`, a JSON array, a JSON string, a JSON number and JSON `null`; and `seed` set to `false`, `0`, `"false"`, `"true"` and integer `1` — then asserts the 6 fabricated rows died, the 24 real ones survived **byte-identically across every column** (`created_at`/`updated_at` included), all 5 `daily_logs` survived byte-identically including one emptied by the purge and one that never had entries, and the `protocols` row is untouched. §6 pins the migration as a **no-op** on a database with no seed rows; §7 pins that it never runs twice, so a seed row planted *after* 0029 (the test-fixture affordance still supports the marking) is left alone. A separate negative control confirmed the assertions have teeth: swapping `json_type` for `json_extract = 1` destroys the `{"seed":1}` row, and dropping the `adhoc` term destroys a row carrying **both** `seed:true` and `adhoc:true`. Note what that second one does *not* say: a real Log-tab capture carries no `seed` key at all, so the marker term already excludes it on its own: the `adhoc` term is defence in depth against a shape no current writer produces, not the thing standing between the owner and their notes.

Both named a specific unverified state of the installed binary. **That assertion has since been removed** — the parenthetical was deleted, and the two comments now say only that the code no-ops *when* the module isn't in the running binary, without claiming it isn't. So the guards no-op and **report** absence rather than asserting it, and `set_reminder` defers to the observed verdict instead of to any comment. (Two caveats hold regardless: iOS asks permission the first time a timed reminder is scheduled and the user can decline, and a reminder with **no time** surfaces in-app only.)
- ✅ **FIXED 2026-08-07 — a one-off reminder no longer resurrects itself every day.** **The mechanism, corrected 2026-08-08** (three places, this one included, previously described it wrong — as a roll-forward re-applied on every resync; executing the pre-fix code disproves that, so do not restore the old wording): `reminderTrigger` used to resolve an *undated* one-off to **TODAY** at its clock time, and return null once that moment had passed. It therefore went **quiet for the rest of that day** — it was never rolled forward to tomorrow, and repeated resyncs within the same day changed nothing. The damage was **per-new-day**: the next day's first resync (app boot, or any Coach turn) re-resolved "today" against the new date, found a fresh future moment and scheduled it again. Nothing marks a one-off done but the user, so "remind me at 9am" fired every day, forever. The symptom was daily-forever; the cause was a day re-derived each new day, not a roll-forward. **The day is now resolved ONCE, at creation.** `createReminder` (`src/lib/db/repositories/reminders.ts`) stamps a concrete local `date` on a one-off that has a time and no date — today if that clock time is still ahead, tomorrow once it has passed, derived from `now`'s local Y/M/D through `todayISODate`, never `new Date('YYYY-MM-DD')`. That makes it a *dated* one-off, which reuses the already-correct dated branch: it fires at that moment and returns null on every resync afterwards. `reminderTrigger` therefore treats a still-undated one-off as unschedulable, and `set_reminder` returns the `date` it actually landed on so the Coach names the right day — and **the confirmation card names it too** (see the entry below). **Legacy undated rows: deliberately NO migration** — a single-user app whose reminder feature is barely used doesn't warrant one, and inventing a firing day for them at some arbitrary boot would re-guess exactly the day this change stopped guessing; they simply stop producing OS notifications and keep surfacing in-app. Lifecycle pinned in `db/reminders.test.mjs` §6 (including the legacy row, month/year rollover, and null on six later resyncs) and `db/coach-tools.test.mjs` §5.
- ✅ **DECIDED + SHIPPED 2026-08-08 — a one-off's date is a "NOT BEFORE" FLOOR for in-app surfacing, not an exact match.** Pinning the day (above) had a side effect nobody asked for: `isDueOn` returned true for a dated one-off *only on its exact date*, so a never-completed "remind me at 9am" vanished from every due-today surface — `get_today_snapshot.remindersDueToday`, `list_reminders.dueToday`, `generateDailyBrief` — from the day after its pinned day, permanently, while the row sat there `active`. Legacy *undated* rows kept surfacing forever, so the asymmetry ran backwards: the well-formed row disappeared and the malformed one nagged. **The semantics now, plainly:** a one-off is due in-app on its date **and on every day after it**, until the user completes or dismisses it; an undated one-off is due any day (the same rule with no floor); daily is always due; weekly is due on its anchor's weekday. Comparison is lexicographic on `YYYY-MM-DD`, which is chronological for that zero-padded shape. **This does not touch OS notifications.** `reminderTrigger` is a separate path and still lapses a passed one-off to null on every resync, so the in-app floor can never resurrect the notification bug — `db/reminders.test.mjs` §6(i) asserts exactly that pairing: a long-overdue one-off is still due in-app across three later days *and* yields null on five repeated resyncs, and completing it stops both. One consequence worth knowing: a **back-dated** one-off ("log the dose I missed on the 1st") is due the moment it is written, since its floor is already behind us.
- ✅ **FIXED 2026-08-08 — today's reminders can no longer be evicted from the Home brief by stale ones.** The floor above had a second consequence this list did not record: an un-dismissed one-off surfaces *forever*, and `listActiveReminders` sorts by **clock time only** — so a months-old 06:00 nudge outranked today's genuine daily and weekly reminders unconditionally, and the brief's `slice(0, 3)` handed the user three dead nudges instead of the day's plan. **The ordering rule now, plainly:** one shared ranked set (`dueRemindersFor(db, today)`, `src/lib/ai/insights.ts`) — **items due on their own day first, in their existing clock order; then overdue one-offs, oldest nag first**, with a source-index tiebreak so nothing depends on `Array.prototype.sort` stability. `daysOverdue` is > 0 **only** for a one-off with a pinned date strictly before today; recurring reminders and undated legacy one-offs are 0, because with no floor there is no age that can honestly be claimed. **In the brief** (`generateDailyBrief`) the set is split in two, so a carry-over can never masquerade as today's plan: **"On deck today: …"** carries only genuinely-today items (first 3 named, the rest counted — ", and 3 more", never silently truncated), and overdue ones get their own clause, **"Still open: Book bloodwork (09:00) — 4 mo overdue."** (first 2 named, rest counted). Ages are a hand-rolled `1 day / 12 days / 4 wk / 4 mo / 2 yr` — **Hermes has no `Intl`** — on the same thresholds as the Screenings ledger's span text. **In the Coach tool**, `get_today_snapshot.remindersDueToday` now projects `{ id, title, time, date, repeat, daysOverdue }`, capped at 10 with a sibling `remindersDueTodayOmitted` count that always ships; because the set is today-first the cap drops the stalest tail *first* — that is an ordering, not a guarantee today's own items survive, since more than 10 due on their own day will trim those as well, which the omitted count then reports. The tool description tells the model that `daysOverdue > 0` is a carried-over obligation it must not present as today's plan. Pinned by `db/insights.test.mjs` §§12–15 (§12 is the exact repro: five months-old one-offs plus a daily and a weekly). **Deliberately unchanged:** `isDueOn`, the notification path, and `list_reminders` — which returns *every* active reminder with a `dueToday` flag, unranked and uncapped, and carries no `daysOverdue`; it never truncates, so nothing can be hidden there. ⚠️ **Same defect, one surface over, still open:** the Coach screen's Reminders card (`src/components/coach/reminders-card.tsx` ← `useReminders` → `listActiveReminders`) renders every active reminder in clock order with no overdue distinction, so an old nudge sits interleaved with today's and gives no hint of its age. Nothing is dropped there, so it under-informs rather than misleads — pointing it at `dueRemindersFor` is the follow-up.
- ✅ **FIXED 2026-08-08 — the write-confirmation card now names the day it is about to pin.** Because a bare-time one-off gets a concrete day stamped at save time, approving *"Set reminder "Call the clinic" at 09:00"* at 22:00 silently wrote a row dated **tomorrow** — the card showed only the clock time, contradicting `write-tools.ts`'s own rule that the confirmation line must carry "what, how much, and (when not today) which day". The fix widened the shared contract rather than softening the rule: `CoachTool.confirmSummary` (`src/lib/ai/tools/types.ts`) takes a third argument — **the same `CoachToolContext` (`{ now }`) `execute` gets** — so a summary resolves the day off the same clock the write will use. (It was introduced as *optional*; it has since been made **required**. See the next entry for why that mattered.) `set_reminder`'s summary calls the very function `createReminder` calls (`resolveOneOffDay`, now exported from the reminders repository) and appends the day whenever it is not today: **`· tomorrow (Sat 8 Aug)`**, `· yesterday (…)`, or `· 2026-08-15 (Sat 15 Aug)` for anything else; a weekly's anchor is always printed as a day, never as "tomorrow". Weekday and month names are spelled out by hand — **Hermes has no `Intl`**, so `toLocaleDateString` is not available on device — and the ISO day is split componentwise, never `new Date('YYYY-MM-DD')`. Pinned in `db/coach-tools.test.mjs` §5 — five assertions: pins-to-tomorrow, silent-when-it-pins-to-today, an explicit ISO day printed with its weekday, a weekly anchor printed as a day, and an untimed one-off whose card is clock-independent because it derives no day at all.
- ✅ **FIXED 2026-08-08 — the card and the row now read ONE clock, so the approved card is the row that lands.** Widening `confirmSummary` (entry above) was only half the fix, and the previous version of this list got the leftover half wrong in two ways at once. **What was actually wrong:** the third argument shipped **optional**, and the one real call site (`src/lib/ai/coach-service.ts`) kept calling `confirmSummary(input, db)` while `execute` minted a *fresh* `new Date()` for itself afterwards — two clock reads with the user's approval sitting between them. **The divergence was never "an exact midnight boundary"**, and threading `{ now }` into the summary call alone would **not** have fixed it, because `execute` still read its own clock; do not restore either claim. It broke at **the reminder's own clock time**: a card rendered at 08:59:30 for "at 09:00" showed a bare time (meaning *today*), and approving it at 09:00:10 wrote a row dated **tomorrow** — the exact contradiction the card was added to prevent. **Now:** `streamCoachReply` holds one clock *factory* for the turn (`options.now ?? (() => new Date())`) and reads it **once per tool call**, above the confirmation gate; that single `CoachToolContext` object goes to both `confirmSummary` and `execute`, and the second `new Date()` is gone. **Per call, not per turn, deliberately** — a turn spans streaming, arbitrary approval latency and up to 8 model round-trips (`MAX_MODEL_CALLS_PER_TURN`), so freezing one instant for a whole turn would date a later `log_meal` to the wrong day across midnight; the window that must not move is card→row. The context argument is now **required**, making a card rendered without the turn clock a type error — optionality is precisely what let the widening sit inert and unnoticed. `db/coach-tools.test.mjs` **§16** drives the real `streamCoachReply` call site (scripted SSE stream; real registry, repositories and SQLite; the clock moved *inside* `confirmWrite` to simulate approval latency) and asserts the straddle writes **today**, that `execute` performed **no second clock read**, and — as a non-triviality control — that the same turn started 40 s later cards *and* writes **tomorrow**. **Three things to know, none of them defects being hidden:** (a) `set_reminder`'s notification check now runs against the card's instant, so in a straddle it can report a schedulable alert for a moment that has just passed — bounded by approval latency, and the OS is the final arbiter; if it ever matters the fix belongs in `src/lib/notifications/reminders.ts`, since schedulability is a live-OS question, not in the tool contract. (b) `write-tools.ts`'s `const now = context?.now ?? new Date();` inside `setReminderTool.confirmSummary` is now **vestigial** — unreachable from the app — and the comments around it still describe the argument as "optional"; a cleanup, not a bug. (c) `StreamOptions.now` is production surface that exists for the tests, matching the codebase's existing `fetchImpl` / `CoachToolContext.now` injection convention; the app never passes it.
- ✅ **DECIDED 2026-08-07 — the app's Documents directory stays PRIVATE: no `UIFileSharingEnabled`, no `LSSupportsOpeningDocumentsInPlace`.** Export writes its JSON into Documents (`src/lib/export/export-file.ts` → `fs.Paths.document`), so the two Info.plist keys were added to `app.json` to surface that directory in the iOS Files app — then **reverted the same day**; `app.json`’s `ios.infoPlist` now carries only `ITSAppUsesNonExemptEncryption`. **The supported route for getting an export off the device is the `expo-sharing` share sheet**, which `export-file.ts` already prefers and which needs no Files-app exposure (`expo-sharing` is already a dependency + plugin, riding the next build). **Correction to the reason first recorded here:** the live DB is *not* in Documents on the pinned version — verified 2026-08-07 against `@op-engineering/op-sqlite@17.1.2`, whose `ios/OPSQLite.mm` passes **`NSLibraryDirectory`** as the base path (Documents survives only as an exported constant, and no `OPSQLite_AppGroup` is set), while `src/lib/db/client.ts` calls `open({ name: 'arc.db' })` with **no `location`** — so `arc.db`, its `-wal`/`-shm` sidecars and the `.pre-migrate-*.bak` snapshots (`getDbPath()` + suffix) all sit under **Library/**. Older op-sqlite releases did default to Documents, which is where that reasoning came from. **The decision stands anyway**, on the surviving risk: publishing Documents hands every export — a complete health record — to any app the user grants access to, permanently and deletably. If Documents exposure is ever wanted, re-verify the base path for the op-sqlite version pinned *at that time*, and if the database has landed there, move it out first with an explicit op-sqlite `location` before either key goes in.
- ⚠️ **Adding a native module that needs an Apple *capability* requires the provisioning profile to be regenerated — a stale cached profile fails the EAS build** with a capability/entitlement mismatch, and the error points at signing rather than at the module you just added. This is the failure mode hit when `@kingstinct/react-native-healthkit` was added: HealthKit is an entitlement, so the App ID must carry the capability *and* the profile must be re-issued afterwards. If a build fails on entitlements right after a native dep lands, clear the cached credentials and let EAS re-generate the profile before debugging anything else.
- ⚠️ **`src/lib/db/repositories/mission-generate.ts` was committed with a LITERAL NUL byte, which makes the file invisible to recursive search.** `planKey` (line ~181) joins a protocol id to an item title with U+0000 — a good delimiter, since it can't occur in either — but it was written as a raw `0x00` byte in the source instead of as an escape. Reproduced 2026-08-07 against the blob at HEAD (13,524 bytes; NUL at offset 6832, line 181): `git diff --stat` reports it as `Bin 13524 -> 13529 bytes` and `--numstat` as `-  -`, which happen only for a blob containing `0x00`; and **ripgrep classifies it as binary and skips it — a recursive `rg`/Grep over a directory returns ZERO matches, silently, exit 1**, whereas naming the file explicitly (`rg planKey <that file>`) returns all 5. A directory-wide search simply lies about this file. (The superseded note also called the file “plain ASCII”: it is not — 67 non-ASCII bytes, `—` × 17, `→` × 4, `§` × 2.) **Fixed in the working tree 2026-08-07** by swapping the raw byte for the escape `\u0000` — runtime-identical, because that escape produces the same U+0000 inside a template literal (asserted directly), and the source of the `+5 bytes`. **The caveat is kept rather than deleted:** any branch or worktree still carrying the committed version is still silently unsearchable. A 2026-08-07 docs pass measured the *already-fixed* working tree, concluded the original audit “does not reproduce”, and wrote a correct finding up as debunked — do not repeat that: check the blob (`git show <rev>:<path>` piped into a byte scan), never the working tree. Unchanged at runtime either way: any `planKey` dumped into a log, a test fixture, or an error message carries an embedded NUL and may print truncated or ragged.

## 3. Design & Styling — Porcelain Ledger

> **The philosophy in one line:** ARC is a beautifully printed lab report that happens to be alive.

Chosen 2026-07-24 from a six-direction exploration (all six specs archived in `docs/design-directions.md` — read that file before proposing any new visual direction). The interface earns trust the way a well-set medical document does: typography, whitespace, hairline rules, and one deep pine-green stamp of authority. Nothing glows, nothing gamifies, nothing is decorated. Bone-white paper is the identity; it will look the same in twenty years, which is the point of an app built for decades.

**How to make something look like ARC:** set it on paper, wrap it in a hairline, headline it in serif, print its numbers in mono, and only reach for pine if it is the one thing that matters on the screen.

Tokens live in `tailwind.config.js` (source of truth for every `className`) and are mirrored in `src/constants/theme.ts` for the few APIs that need literal colour strings (navigation theme, icon `color` props). **Any palette change must touch both files.**

> **The pine discipline rule (sacred):** pine appears on exactly five things — the "Do this next" hero (its soft surface, top rule, eyebrow, and Done button), primary actions (send button, a card's single CTA like "Open chat"), **completion stamps** (checkmark circles, the mission progress fill — completion is what pine *means*), the user's own chat bubbles, and the active tab. Plus two sanctioned micro-accents: the 1.5px "Coach presence" dot beside ARC-Coach eyebrows and the streaming caret. Nothing else. Not links-in-general, not decorations, not headings. If everything is emphasised, nothing is directive — the entire design stands on this restraint.

> Signal colours mark **biological states only** (readiness dot, segment bar, metric values carrying a verdict) — never UI chrome. Known accepted weakness from the design critique: `good` (olive) sits between `optimal` (green) and `caution` (amber) as a saturation slide rather than a distinct hue; direction F's categorical green/blue/gold/red taxonomy is the fix if the segment bar ever reads ambiguously on device.

### Light only — by decision, not omission
ARC is **light-mode only**: `userInterfaceStyle: "light"` in app.json, an unconditional nav theme in `app/_layout.tsx`, `StatusBar style="dark"`, and **zero `dark:` variants anywhere in the codebase** (a grep for `dark:` in app/ and src/ should return nothing — if it returns something, someone broke the system). Paper is the identity; a "dark porcelain" would be a different, worse design. If ARC ever needs a night mode, the archived **Night Watch (B)** direction is the designed candidate — it would be a second complete theme, not `dark:` variants bolted onto this one. See the ADR in `docs/decisions.md`.

### Typography — three voices
| Voice | Family | Used for | Class |
| --- | --- | --- | --- |
| **Serif** (authority) | Iowan Old Style → Palatino → Georgia (iOS system serifs) | Headlines, screen titles, the readiness verdict, "Today's Mission", "Today is handled" | `font-serif font-semibold` |
| **Sans** (voice) | System default | Body text, briefs, item titles, buttons, chat | (default) |
| **Mono** (data) | Menlo → Courier New | **Every measured value**: times (07:15), counters (3 of 11), metric values (42 ms), hero metadata line, segment-bar labels, the PREVIEW badge | `font-mono` |

The serif/mono split carries meaning: **serif speaks, mono measures.** A number set in mono is a datum; if you find a standalone measurement in sans, fix it. One deliberate exception: numbers **inside prose** (the readiness detail line, the Coach's sentences) stay sans — splitting fonts mid-sentence reads worse than the rule is worth. Eyebrows are 11px uppercase with `tracking-[2px]` (the "2px tracking" of the spec — not `tracking-widest`, which is em-relative).

> ⚠️ **Font-stack gotcha (cost an hour):** define `fontFamily` in tailwind.config.js as a plain **array** of family names. Do NOT use `nativewind/theme`'s `platformSelect` — its custom-function CSS syntax cannot carry a family name containing spaces, and "Iowan Old Style" silently compiled to an **empty declaration** (verified in the bundle's style registry). Plain CSS stacks parse correctly; native picks the first family.

### Shape & rhythm
- Cards: `rounded-card` (10px). Buttons: `rounded-btn` (6px). **No pills, no 24px super-rounding** — this is print, not bubblegum. Chat bubbles use `rounded-card` with one squared corner (`rounded-br-sm` user / `rounded-bl-sm` coach) like a ledger tab.
- **No shadows, no elevation, no glow — anywhere.** Layering is done with hairline borders and the paper/porcelain two-tone.
- The hero is "a stamped ledger entry": `border border-pine-tint` + `border-t-[3px] border-t-pine` on `bg-pine-soft`.
- **Rules enclose objects, never pages** (owner call, 2026-07-24, after device review). A hairline is correct on a **card edge** and **between rows of one list**, because both times it is drawing the boundary of a single object. A rule laid across the page to separate two sections is furniture: put one above a short block and one below it and you have drawn a box around it — which is exactly what the owner flagged. **Sections are separated by whitespace only.** If a section can't hold its own without a rule, it needs a heading or more air, not a line.
- Section rhythm on Home: `mt-5`–`mt-9`; airy density is part of the calm, and since the de-boxing pass it is the *only* thing separating sections, so don't tighten it casually.
- One shared container: `Screen` (`src/components/ui/screen.tsx`) — safe-area, `px-5` gutter, `bg-paper`.
- Tap targets are whole rows/cards; the IA target is ≤ 2 taps to act.

### Surface treatments (the recipes)
- **Card:** `rounded-card border border-hairline bg-porcelain p-4`.
- **Hero:** pine-soft + pine top rule (above); serif title; mono metadata; Done = solid pine `rounded-btn`; Snooze = `border-hairline-strong` ghost; Skip = bare muted text.
- **Eyebrow:** `text-[11px] uppercase tracking-[2px] text-ink-muted` (+ `font-medium` when it labels a section). The date eyebrow is bare — no folio rule under it (see "rules enclose objects" above).
- **Segment bar:** flat `h-[6px]` rectangles, `rounded-[1px]`, `gap-0.5`, mono-caps labels beneath. A typeset gauge, not a chart.
- **Mission row:** hairline-soft separators; pine-filled circle when done; times in mono; completed text drops to ink-muted.
- **Chat:** user = solid pine slip, right; coach = bordered porcelain slip, left. The Coach reads as typeset prose, not chat froth.
- **Metrics:** mono `text-lg font-semibold` values coloured by signal only when they carry a verdict; labels are eyebrows. No section heading — every cell already carries a caps label, and stacking caps on caps is noise; the 2×2 grid is its own boundary.

### Patterns worth reusing
- **Derived emphasis:** the hero isn't authored separately — it's the first unresolved mission item (`src/lib/home/derive-mission.ts`). One source of truth, so the UI can't contradict itself.
- **Whole-string class maps** for dynamic styles (`src/components/home/signal.tsx`): Tailwind only sees class names that appear literally in source — never build `bg-signal-${level}`.
- **Explicit hairlines**, not `divide-y` — that utility needs a CSS sibling selector RN doesn't have.

### Open design questions
- ⚠️ **Serif rendering on device** — Iowan Old Style at 600 weight on a real iPhone; if it renders as fake-bold or too bookish, Palatino is the next candidate in the stack. *Not raised in the 2026-07-24 device review, which is weak evidence it's fine — the owner was looking at boxes, not letterforms. Still unconfirmed.*
- ⚠️ **Pine-soft hero on paper** — enough contrast between `#E7EEE6` and `#F6F3EC` at real brightness? If the hero doesn't pop, deepen pine-soft before reaching for shadows (there are no shadows). *Same caveat: not raised, not confirmed.*
- ⚠️ **Does the metrics strip still land without its rule?** It is now the last thing on the screen with nothing but whitespace above it. If it reads as orphaned rather than quiet, the fix is more space or a serif heading — not the rule back.
- 📋 Extract shared primitives (Card, Eyebrow, GhostButton) once a third screen needs them, not before.
- 📋 Ionicons work but read slightly rounded against the print aesthetic; a stroke-consistent set is a candidate refinement.
